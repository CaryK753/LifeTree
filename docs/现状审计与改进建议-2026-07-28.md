# LifeTree 现状审计与改进建议

- 日期：2026-07-28
- 作者：wwj
- 范围：项目计划书、前后端实现、single/multi 模式、本地桌面存储、普通用户体验

## 1. 总体判断

LifeTree 已经具备目标、画像、信源、审核、图谱、情景、推演、通知和 AI 对话的完整外形，但计划书的“已实现”口径偏乐观。当前主要问题不是页面数量不足，而是以下四类闭环仍不完整：

1. **决策可信度**：推演公式与业务语义存在根本冲突，结果可能稳定地产生错误信心。
2. **首次使用与日常使用**：功能入口多，但缺少模板式立项、明确的下一步和跨模块搜索。
3. **模式与数据归属**：single/multi 只是鉴权开关，尚未形成可逆、可解释的数据迁移流程。
4. **本地产品形态**：PWA 不等于本地桌面客户端，现有运行仍依赖 4 类基础设施和后台任务组件。

## 2. 计划书与代码差距

### P0：上线前应解决

| 问题 | 当前实现 | 风险 / 建议 |
| --- | --- | --- |
| 推演聚合语义错误 | `bayesian.py` 与 `monte_carlo.py` 使用 `1 - Π(1-p_i)` 聚合“各要求成功率” | 因子越多，成功率反而越接近 100%。Requirement 通常是 AND 门，不应使用 noise-OR。需要按“硬门槛 / 可替代条件 / 风险事件”建模，并用标定数据验证。 |
| single → multi 无数据认领 | 默认用户数据固定属于 `000...001`，注册用户得到新 ID | 切换后用户会感觉数据“消失”。切换前必须选择：认领到管理员、保留为共享模板、导出后清空，且提供预览与回滚。 |
| 服务失败会永久“加载中” | 首页等页面只处理 `isLoading`，不处理 SWR `error` | 后端、数据库或代理不可用时用户不知道发生了什么。所有主页面需要统一错误态、重试和组件健康入口。 |
| multi 离线缓存串号 | Service Worker 原先缓存所有成功 `/api/` GET，缓存键未按用户隔离 | 同设备换账号或离线可能显示上一账号数据。本次已改为 API network-only；以后若恢复离线数据，必须使用按用户加密的本地数据库。 |

### P1：核心产品闭环缺失

| 计划能力 | 实际状态 | 建议 |
| --- | --- | --- |
| 场景模板市场 | 只有 seed 脚本与演示数据，没有模板浏览、预览、导入、版本升级 UI/API | 先做 3 至 5 个官方模板，不急着做社区市场。 |
| 三问渐进向导 | 首页有引导卡，目标仍以普通表单创建 | 新用户首屏直接进入三问向导，先生成草案，再按关键路径渐进补资料。 |
| 家庭/多角色协同 | 模型有 `joint_profiles` 读取属性，前端无家庭成员编辑、权限或并排主申方案 | 先实现同账号家庭沙盘，再做邀请、评论和只读分享。 |
| 多渠道通知 | Email 与站内信可用，SMS 明确为 stub，Web Push 无订阅/权限链路 | UI 不应把未接通通道表现为可用；先完成 Web Push，再按市场选择短信网关。 |
| OAuth 八预设 | Apple 预设没有 userinfo，后端也未解析 `id_token`；并非真正可用 | 未实现前隐藏 Apple，或完整支持 Apple client-secret JWT、nonce 与首次授权资料。 |
| 多模型协议 | `anthropic` 可被选择，但通用 client 始终构造 OpenAI SDK | 协议能力与实际 client factory 对齐；无法调用的协议不得在 UI 显示为可用。 |
| 深度预测 | 有随机模拟和图表，但参数主要来自固定启发式 | 在有真实标定数据前应标为“探索性估计”，展示假设、样本来源和敏感性，避免伪精确。 |
| 完整本地能力 | PWA 缓存页面壳，业务数据仍依赖服务端 | 本地桌面应另建 local storage profile，详见第 6 节。 |

### P2：已实现但仍需收口

- 冲突分支已有两套路径：`structuring._spawn_review_branch` 与 LangGraph conflict graph，需要明确唯一入口，避免重复分支。
- 图谱使用 PostgreSQL 真相源 + Neo4j 镜像，但 UI 缺少“镜像延迟/同步失败”状态。
- 插件目前是 AST 黑名单与同进程执行，不是安全沙箱；多用户服务不应默认允许普通用户运行不可信插件。
- PWA 声称可查看最近数据，但为保证 multi 隔离，本次已停止缓存 API；文案和计划书应改成“页面壳离线”，直到有用户隔离存储。
- 代码文件普遍远超团队限制，例如 `profile/page.tsx`、`platform-config.tsx`、`chat-panel.tsx`；这会直接放大 UI 回归与状态耦合风险。
- 当前 TypeScript 基线不通过，存在场景 toast/badge 类型、sources 缺少导入及 Cytoscape 类型冲突；应恢复 CI 的 `type-check` 绿灯。

## 3. 普通用户视角的别扭点

### 首次使用

- 首屏侧栏一次暴露十余个入口，用户还没有目标时就需要理解“目标罗盘、决策关系图、情景、信源、审核、录入、插件”的差异。
- 首页同时推荐 AI 对话和“画像 → 目标 → 录入”三步，主路径不唯一。建议只保留“使用模板”与“告诉 AI 我的目标”两个入口。
- AI 对话依赖模型、角色和外部服务配置，但首次使用没有 readiness 检查；失败后用户很难知道是模型、后端还是数据不足。
- 创建目标后仍需跨多个页面补路径、要求、信源、情景，缺少一个能持续显示完成度的项目工作台。

### 日常使用

- 产品强调长期决策，但缺少统一的**行动日历 / 待办 / 截止日提醒**。用户最终仍要回到日历或任务软件。
- 缺少跨目标、信源、事件、记忆和对话的**全局搜索**。
- 缺少“自上次访问以来发生了什么”的变更摘要，长期等待用户只能逐页检查。
- 图谱和概率图信息密度高，但关键结论与“我今天该做什么”距离较远；建议所有分析页固定保留 1 至 3 个下一步动作。
- 用户纠正 AI 抽取后缺少统一的撤销、版本历史和影响预览，不利于建立信任。
- 术语边界不够自然：“信息来源 / 信息录入 / 待审核”是同一工作流，却分成三个一级入口。

### 账户与数据

- 没有普通用户自助找回密码，代码注释声称可恢复，但实际只有管理员重置。
- 仅聊天支持导出，缺少整库备份、恢复和迁移；对“人生长期数据”产品这是基本信任能力。
- single 模式仍允许创建和登录真实账户，语义更像“允许匿名默认用户”，不是严格单用户，容易误解数据落在哪个身份下。
- single 模式若暴露到公网，任何匿名访问者都拥有默认用户能力和平台配置权限；产品应明确标为“仅可信本机/内网”。

## 4. single / multi 模式建议

模式应拆成两个正交概念：

- `identity_mode`：`personal` / `multi_user`
- `storage_mode`：`full` / `local`

建议规则：

1. `personal + full`：当前 single 的替代，匿名默认身份，仅建议本机或可信内网。
2. `multi_user + full`：当前 multi，强制登录、严格租户隔离、禁止共享 API 缓存。
3. `personal + local`：桌面客户端默认组合，SQLite + 本地文件 + Ollama，不要求 OAuth。
4. 暂不支持 `multi_user + local`，避免把桌面版本变成另一个服务器产品。

切换模式前应运行 preflight：检查是否存在真实管理员、默认用户数据量、待执行任务、OAuth/Passkey 配置，并给出迁移计划。切换不是一个即时 toggle，而是带确认、进度、结果摘要和回滚点的操作。

本次已修复：

- multi 首启无真实用户时，匿名“切换到 single”不再被依赖注入提前 401。
- `/auth` 未登录时不再请求 `/auth/me`，SSE 也不会挂载。
- multi 登录后的 SSE 改用携带 Bearer token 的 fetch stream。
- Service Worker 不再缓存受保护 API 响应。

## 5. OAuth 修复说明

- 回调路径可继续使用 `github/google` 等名称，但数据库统一保存配置中的 canonical provider ID。
- Profile 读取与解绑兼容历史名称型绑定，不要求人工改数据库。
- OAuth 用户资料统一处理常见 `email/mail/emailAddress/preferred_username` 与多种头像字段。
- GitHub `/user` 未返回私有邮箱时，会请求 `/user/emails` 并选择 primary + verified 邮箱。
- Discord hash 头像和 Facebook 嵌套 picture URL 已归一化。
- OAuth 再次登录时，可把历史 `@lifetree.local` 占位邮箱回填成真实邮箱。

## 6. SQLite 本地桌面模式

### 是否有必要

**有必要，但它不是“把 PostgreSQL URL 换成 SQLite”这么简单。** 如果目标是数据完全在本地、普通用户双击即可使用，那么当前 PostgreSQL + Neo4j + Redis + MinIO + Celery 的部署成本与产品目标冲突。

### 推荐的 local profile

| 当前组件 | 本地替代 |
| --- | --- |
| PostgreSQL + JSONB + pgvector | SQLite JSON1/FTS5；向量先用 sqlite-vec 或小数据量进程内余弦检索 |
| Neo4j | 关系边表 + SQLite recursive CTE；复杂分析加载到 NetworkX |
| Redis pub/sub / OAuth state | 进程内事件总线；local 模式默认不启用 OAuth |
| Celery worker / beat | 进程内任务队列 + APScheduler，应用退出时可恢复任务 |
| MinIO | 应用数据目录下的内容寻址文件存储 |
| Docker Compose | Tauri/Electron 外壳 + FastAPI sidecar，或后续改为纯本地服务层 |

### 实施顺序

1. 先定义 Storage、BlobStore、GraphStore、EventBus、JobRunner 接口，不直接在 API 中判断 SQLite。
2. 将 PostgreSQL 专用的 `JSONB`、`Vector` 与数据库默认值封装到 full adapter。
3. 实现 local adapter，并先支持目标、画像、信源、事件、情景、聊天与备份恢复。
4. 图谱、向量和任务调度按数据规模渐进增强，不要求首版完全复制服务端拓扑。
5. 增加加密备份、导入/导出和数据库 schema migration，这是桌面版发布门槛。

## 7. Ollama

本次已增加一等 `ollama` 协议/预设，默认地址为 `http://127.0.0.1:11434/v1`，允许空 API Key，并复用现有 OpenAI-compatible client。后续还需要：

- 自动探测 `/api/tags` 并导入已安装模型。
- 标注模型能力，避免把不支持 vision/embedding 的模型错误分配到对应角色。
- 桌面环境中将 `127.0.0.1` 明确解释为用户主机；Docker full 模式则需要 `host.docker.internal` 或可配置地址。

## 8. 建议路线

1. **可信度冲刺**：修正推演聚合、建立校准测试集、统一错误态、恢复 TypeScript CI。
2. **个人版闭环**：模板向导、行动日历、全局搜索、变更摘要、整库备份恢复。
3. **模式治理**：single 数据认领、切换 preflight、权限与插件安全边界。
4. **本地桌面 MVP**：SQLite + 本地文件 + Ollama + 进程内任务，先支持 personal 模式。
5. **协作与渠道**：家庭沙盘、分享评论、Web Push、真实短信，再考虑模板市场和 B2B。
